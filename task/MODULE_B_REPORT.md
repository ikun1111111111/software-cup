# 模块 B 实现报告：数字人体验

## 做了什么

模块 B 围绕"数字人体验"展开，目标是让游客在灵山胜境景区能够通过数字人进行语音对话、观看表情和口型同步的导览，并在网络不佳时依然能获得基本服务。整个模块从 TTS 语音合成的底层能力开始，逐步搭建了流式音频传输、口型驱动、表情控制、悬浮助手交互面板、离线缓存、方言切换等完整链路。

本次实现共新建 13 个文件，修改 19 个文件，新增约 880 行代码，编写 116 个测试用例且全部通过。

---

## 后端做了什么

### 语音合成从同步变成流式

原来的 TTS 模块只能一次性返回完整音频。改造后新增了 `synthesize_stream()` 异步生成器，它会把一段语音拆成多个小块，每块附带对应的音素时间戳，通过 SSE（Server-Sent Events）逐块推送给前端。这样前端可以在音频还没完全生成完的时候就开始播放，用户感知到的等待时间大幅缩短。

对应的 API 端点是 `POST /api/tts/stream`，它接收文本和可选的 voice 参数，返回事件流，每个事件包含一段 base64 编码的音频数据和一组音素信息。另外还提供了 `POST /api/tts/cache` 用于查询某段文本是否已被缓存，避免重复合成。

### 音素时间戳让口型可以精确对齐

音素时间戳是口型同步的基础。系统对输入文本逐字分析，通过 pypinyin 判断每个字的声母类型，将其归类为三种口型：闭合（声母，如 b/p/m）、半开（介音或鼻音）、全开（韵母，如 a/o/e）。每个音素携带毫秒级的起止时间，前端拿到后可以逐帧匹配当前播放位置来驱动嘴巴张合。

这套方案在没有真实 CosyVoice 音素输出的情况下，用启发式规则提供了合理的近似；当 CosyVoice 可用时，可以直接替换为真实的音素数据，无需改动前端逻辑。

### 方言支持不是换个参数那么简单

系统预置了三种语音：普通话、南京话、四川话。每种方言在后端配置中对应不同的 speaker_id，通过 `_resolve_voice()` 函数统一解析。这个函数做了向后兼容处理——如果传入的 voice_id 在预置列表中找不到，会回退到普通话，避免因配置错误导致合成失败。

新增的 `GET /api/tts/voices` 端点让前端可以动态获取可用语音列表，而不是硬编码。

### 离线包让没网也能导览

离线包是一个 JSON 文件，包含灵山景区的 50 条常见问答、5 个核心景点的详细信息（名称、描述、经纬度、建议游览时长）以及 5 个音频导览的引用路径。

生成脚本 `scripts/generate_offline.py` 会把这些数据打包写入 `data/offline/offline_package.json`。API 端点 `GET /api/offline/package` 负责下发这个文件，支持 ETag 和 If-Modified-Since 两种条件请求——如果客户端已经有了最新版本，服务器直接返回 304 Not Modified，节省带宽。`GET /api/offline/status` 则告诉客户端包是否可用、有多大、有多少条目。

## 前端做了什么

### 口型同步的两条路径

LipSync 组件现在支持两种驱动模式。优先使用后端返回的音素时间戳数组——每个音素有明确的起止时间和口型分类，组件在每一帧检查当前播放时间落在哪个音素上，然后设置 Live2D 的 ParamMouthOpenY（嘴巴张开程度）和 ParamMouthForm（嘴角形状）。如果没有音素数据，自动降级到 WebAudio 频谱分析，通过 AnalyserNode 的频率数据来估算口型。

为了让口型更自然，还加入了 ParamAngleZ 参数让头部随说话节奏轻微左右摆动，幅度很小但效果明显。

### 流式音频的前端处理

AudioSync 组件新增了 `audioChunks` prop，接收一个 base64 字符串数组。当这些数据块到达时，组件把它们解码为二进制，拼接成一个完整的 Blob，创建 Blob URL 交给 Audio 元素播放。播放过程中持续把当前时间（毫秒）同步给 LipSync，形成"播放时间 → 音素匹配 → 口型更新"的闭环。

### 表情系统对齐了业务语义

原来的表情类型是 `positive` 和 `negative`，过于抽象。现在改为 `smile`（微笑）、`think`（思考）、`sorry`（抱歉）、`surprise`（惊喜）、`neutral`（中性）五种，每种映射到具体的 Live2D 参数组合。表情切换时有 300ms 的渐变过渡，不会生硬跳变。

数字人主组件 DigitalHuman 现在可以从 ChatResponse 中接收 emotion 字段，自动切换到对应表情。

### 悬浮助手是全局的交互入口

FloatingAssistant 是一个可以拖拽的悬浮球，固定在屏幕右下角，48 像素大小，蓝色渐变背景。点击后展开为一个 340 像素宽的对话面板，包含消息列表、文本输入框和语音按钮。

它有几个设计细节：收到新消息时如果面板是收起状态，悬浮球会有一个 150 毫秒的弹跳动画并显示红点提示；支持 Ctrl+K 快捷键切换面板状态；监听页面上的 `entity:click` 事件，当用户点击景点等实体时自动展开面板。面板通过 `scrollIntoView` 自动滚动到最新消息。

这个组件在 App.tsx 中全局挂载，不依赖任何路由，任何页面都能使用。

### 语音交互更加细腻

VoiceInput 组件的改动集中在三个方向。第一是语速调节：新增一个设置按钮，点击后显示 0.5x 到 2x 的滑块，用户选择的语速会保存到 localStorage，下次打开自动恢复。第二是打断功能：用户按下语音按钮时立即触发 `onInterrupt` 回调，通知数字人停止当前播报。第三是实时转写：录音过程中如果有 ASR 结果，会在按钮下方实时显示当前识别的文字。

长按 300 毫秒触发录音的设计保持不变，短按不会误触发，鼠标离开会取消长按。

### 离线缓存用 IndexedDB 实现

offlineCache 服务把离线包数据存入 IndexedDB，分三个 store：qa_pairs 存问答、scenic_spots 存景点、meta 存版本和缓存时间等元数据。

`syncOfflinePackage()` 函数负责从服务器拉取离线包并缓存，它会先检查服务器端的包是否可用，然后带上本地的 ETag 发请求，如果是 304 就跳过下载。`searchCachedQA()` 提供基于关键词的本地搜索，`onNetworkChange()` 监听浏览器的 online/offline 事件并通知调用方。

### 方言和形象可以自由切换

VoiceSelector 是一个下拉选择器，默认提供普通话、南京话、四川话三个选项，选中后保存到 localStorage。AvatarSelector 类似，提供古风、现代、卡通三种数字人皮肤风格。两个组件的设计一致：点击按钮展开下拉，选中项高亮，点击外部关闭。

## 测试覆盖了什么

后端 25 个测试覆盖了 TTS 合成的基本流程（空文本、降级处理、缓存命中/未命中）、音素时间戳的 schema 和分类逻辑、五种 voice 解析场景、流式合成的事件序列、离线包的下载和条件请求。

前端 91 个测试分布在七个文件中：EmotionController 的五种表情映射和过渡动画（11 个）、LipSync 的音素驱动和频谱分析两条路径（10 个）、AudioSync 的流式音频拼接和时间同步（23 个）、FloatingAssistant 的展开收起和消息交互（11 个）、VoiceInput 的长按录音和语速调节（18 个）、offlineCache 的缓存读写和搜索（8 个）、VoiceSelector 和 AvatarSelector 的选择和持久化（10 个）。

## 做了哪些关键决策

用 SSE 而不是 WebSocket 做流式 TTS，是因为 SSE 更简单、天然支持重连、且语音合成是单向推送不需要双向通信。音素分类用 pypinyin 的声母判断而不是依赖 CosyVoice 的真实输出，是因为开发阶段 CosyVoice 不一定可用，启发式规则提供了合理的降级。表情类型用业务语义（smile/think）而不是技术参数（positive/negative），是因为前端组件需要直接映射到 Live2D 参数，语义化的类型更直观也不容易出错。悬浮助手全局挂载而不是放在某个页面内，是因为它需要在任何页面都能被唤起。离线缓存用 IndexedDB 而不是 localStorage，是因为问答数据可能有几十条，localStorage 有 5MB 限制且不适合结构化查询。
