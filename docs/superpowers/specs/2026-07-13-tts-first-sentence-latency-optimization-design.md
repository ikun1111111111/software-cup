# TTS 首句延迟优化设计

## 目标

在不重构现有播放器协议的前提下，降低 Expo Web 聊天场景中用户从提交问题到听到第一句语音的等待时间。优化后保留 CosyVoice v3、完整 MP3、口型时间戳、语音队列和现有降级链。

## 已测基线

- CosyVoice 短文本直接合成约 2.4 秒，43 字文本约 3.9 秒。
- `/api/tts/cache` 首次请求约 3.8 秒。
- 设计阶段的 `/api/tts/stream` 首个音频事件约 3.0 秒，当时接口会先完成整段合成，再切分 MP3 字节。
- Redis 未运行时，全局限流中间件每个请求额外等待约 1 秒；缓存命中请求仍约 1 秒。

## 范围

本次实现两项低风险优化：

1. Redis 限流失败熔断，移除重复的固定连接超时。
2. 聊天答案首句完成后提前发起 TTS 请求，并在答案完成时优先播放已预取的首句，再通过现有单槽语音队列播放剩余文本。

首句预取主体方案不依赖播放器协议变化。交付审查阶段额外接入了 CosyVoice 原生 WebSocket 音频回调，Web SSE 可渐进返回音频；MediaSource 播放器和原生端逐块 MP3 播放仍不在本次范围内。

## 方案一：Redis 限流熔断

### 数据流

1. 第一个请求照常访问 Redis 限流器。
2. Redis 连接失败时记录 `retry_after = monotonic() + 30s`，本次请求继续放行。
3. 熔断窗口内的后续请求跳过 Redis 限流检查，直接进入业务路由。
4. 窗口结束后允许一个请求重新探测 Redis；成功则恢复正常限流，失败则重新开启熔断窗口。

### 约束

- Redis 正常时限流语义不变。
- Redis 不可用时沿用当前“故障放行”策略，只消除重复等待。
- 熔断状态仅保存在当前后端进程中，不引入新依赖或持久化。

## 方案二：首句 TTS 预取

### 首句判定

- 聊天 SSE 收到 `token` 后，检查累计答案是否出现第一个完整句末标点：`。！？!?；;`。
- 仅预取第一个非空完整句；逗号不视为首句结束，避免过短、语义不完整的语音片段。
- 每次用户问题最多启动一次首句预取。

### 缓存与并发

- `useVRMSync` 的 TTS 内存缓存保存 `Promise<TTSResult>`，而不是只保存已完成结果。
- `prefetchSpeech(text)` 与正式播放复用同一 Promise，避免预取未完成时重复请求。
- 请求失败时从缓存删除，正式播放仍进入现有浏览器语音或视觉动画降级。
- 缓存仍限制为 20 条。

### 播放顺序

1. 首句预取完成前不启动口型和动作。
2. 收到 `done` 后，如果最终答案仍以已预取首句开头：
   - 立即提交首句播放；
   - 将剩余文本提交给现有 `VRMManager.pendingSpeech` 单槽队列；
   - 首句实际播放结束后，现有 `stopSpeaking(playQueued=true)` 自动启动剩余文本。
3. 如果答案被服务端改写、没有剩余文本或首句不匹配，丢弃分段方案并按当前完整答案播放。
4. FAQ、缓存命中、本地答案和非聊天页面维持当前完整文本播放，不额外拆分。

## 模块变更

- `backend/app/core/rate_limiter.py`
  - 增加 Redis 故障熔断状态和辅助函数。
  - 中间件与路由级 dependency 共用熔断判断。
- `backend/tests/test_rate_limiter.py`
  - 覆盖首次失败开启熔断、熔断期跳过 Redis、冷却结束恢复探测。
- `software/mobile/hooks/useVRMSync.ts`
  - TTS 缓存改为 Promise 缓存。
  - 对外提供 `prefetchSpeech(text)`。
- `software/mobile/hooks/useDigitalHumanDriver.ts`
  - 透传 `prefetchSpeech`。
- `software/mobile/app/(tabs)/chat.tsx`
  - token 阶段识别并预取首句。
  - done 阶段仅在预取首句与最终答案匹配时分成首句和余文两段播放。
- 移动端测试
  - 覆盖首句提取、单次预取、Promise 复用、答案不匹配回退和两段队列播放。

## 错误处理

- Redis 熔断只记录一次警告，熔断窗口内不重复刷日志。
- 首句预取失败不影响文字回答，也不阻止最终完整答案走原有 TTS/浏览器语音降级。
- 新问题、重置会话、离开页面时清除本轮预取引用，旧答案不能触发新会话播放。

## 验收标准

- Redis 不可用时，第一个业务请求允许出现连接超时；随后 30 秒内的请求不再承担约 1 秒 Redis 延迟。
- Redis 正常时现有限流测试保持通过。
- 流式答案出现首个完整句后立即启动一次 TTS 预取。
- 最终答案匹配时，首句播放复用预取请求，剩余文本随后自动播放且不覆盖首句。
- 最终答案不匹配或预取失败时，行为与当前完整答案播放一致。
- TTS 专项测试、移动端 TypeScript 检查和相关聊天/VRM 测试通过。

## 后续可选优化

若首句预取和 Web SSE 渐进音频仍不能满足体验目标，再单独设计 MediaSource 播放器与原生端增量 MP3 解码方案。
