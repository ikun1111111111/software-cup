# 移动端 VRM 随机待机动作调度设计

## 背景

移动端多个页面分别挂载 `VRMView`，每个实例都会创建自己的 `VRMDemoActionPlayer`。播放器当前将 `idleDueAt` 初始化为 `0`，因此页面挂载后的第一帧必然满足触发条件，表现为数字人每进入一个页面都会立即播放待机动作。

播放器在后续动作结束后已经使用 4.5–8.5 秒的随机间隔，但该随机节奏不会跨页面保留。

## 目标

- 页面进入和页面切换不直接触发待机动作。
- 所有移动端页面共享同一条随机待机时间线。
- 待机动作继续从 `waiting1`、`waiting2`、`waiting3` 中随机选择。
- 说话或执行显式动作时不播放随机待机动作。
- 保持现有 4.5–8.5 秒随机间隔，不扩大本次改动范围。

## 方案

在 `vrmDemoActionPlayer.ts` 中增加一个模块级轻量调度器，保存下一次待机动作允许触发的绝对时间。各页面创建的播放器实例共享该调度状态，而播放器仍负责具体 GLB 动作的加载、播放和清理。

调度器使用绝对时间而不是 `VRMView` 挂载后的局部 `elapsed`，因此页面切换不会重置倒计时。第一次调用只安排下一次随机触发时间，不播放动作。

## 调度流程

1. 应用首次进入可待机状态时，生成当前时间加 4.5–8.5 秒的下一次触发时间。
2. 页面切换时，新播放器读取已有触发时间，不重新安排，也不立即播放。
3. 到达触发时间且当前没有说话、没有显式动作时，当前可见播放器领取本次触发，从三个 waiting 动作中随机选择一个播放。
4. 领取触发时立即安排下一次随机时间，避免多个仍挂载的页面实例重复领取。
5. 开始说话、切换到显式动作或待机动作结束时，将下一次触发适当延后，避免动作连播或与业务动作重叠。
6. 单个播放器卸载只清理自己的动画资源，不清空全局调度时间。

## 模块边界

### 全局待机调度器

- 输入：当前绝对时间、是否允许待机。
- 输出：本帧是否获得一次待机动作触发权。
- 状态：下一次允许触发的绝对时间。
- 可测试性：随机数和当前时间通过参数或小型纯函数控制，以便编写确定性测试。

### `VRMDemoActionPlayer`

- 保留动作规范化、GLB 加载、骨骼重定向和播放逻辑。
- 在满足 `requestedAction === 'none'` 且未说话时向全局调度器申请触发。
- 收到触发权后随机选择 waiting 动作。
- `dispose()` 不重置全局调度状态。

## 边界情况

- 说话期间到达触发时间：不播放，重新延后随机间隔。
- 显式动作期间到达触发时间：不抢占动作，重新延后随机间隔。
- 多个 Tab 页面仍保持挂载：调度器采用先领取后重排，保证一次只触发一个播放器。
- 应用进程重新启动：重新建立随机时间线，不要求持久化到本地存储。
- GLB 加载失败：保持现有告警行为，后续仍按新的随机时间继续尝试。

## 测试

1. 首次更新不会立即触发 waiting 动作，只会安排随机截止时间。
2. 新播放器实例不会重置已有的全局截止时间。
3. 截止时间到达后只允许一个实例领取触发。
4. 说话和显式动作会阻止随机待机动作并延后下一次时间。
5. 触发的动作只能是 `waiting1`、`waiting2`、`waiting3`。
6. 现有动作播放、语音动作暂停和动作完成测试保持通过。
