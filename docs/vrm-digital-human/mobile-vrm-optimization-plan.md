# 移动端 VRM 数字人优化方案

> 日期：2026-06-26  
> 范围：`software/mobile` 移动端 VRM 数字人体验、交互链路、性能与比赛演示保障  
> 目标：对齐赛题截图中的“游客交互端、形象生成与驱动、核心技术指标”要求，把 VRM 从展示组件升级为主动导览主角。

## 1. 方案结论

移动端 VRM 的下一步重点不是继续堆功能，而是把现有能力收束成一个清晰、稳定、可演示的“AI 数字人导游”闭环：

```text
打开 App
  -> 小灵主动欢迎
  -> 采集游玩时长/兴趣
  -> 推荐路线
  -> 地图导航
  -> 到点讲解
  -> 语音/文字问答
  -> 口型、字幕、表情、动作同步反馈
  -> 生成旅行记忆
  -> 行为数据回流后台
```

建议将移动端 VRM 的产品定位从“右下角浮窗助手”提升为“页面首屏可见、流程中主动陪伴、关键节点可解释”的数字人导览员。评委需要第一眼看到数字人，第二眼看到它能带路、能讲解、能问答，最后看到系统有可量化的准确率、延迟和稳定性指标。

## 2. 截图要求映射

### 2.1 游客交互端

截图强调的能力包括数字人形象展示、多模态交互、情感互动、智能问答、路线规划与讲解、创新探索。移动端应对应为：

| 截图要求 | 移动端落点 | 优化方向 |
|---|---|---|
| 数字人形象展示 | 首页/探索页/导览页中的小灵 VRM | 首屏舞台化，避免只作为角落浮窗出现 |
| 多模态交互界面 | 文字输入、语音输入、快捷问题、按钮反馈 | 保留文字兜底，语音回答必须有字幕 |
| 情感互动 | 表情、动作、语气、字幕气泡 | 建立场景到表情/动作的稳定映射 |
| 智能问答 | 本地 FAQ + 后端 RAG + TTS | 常见问题本地优先，复杂问题走知识库 |
| 路线规划与讲解 | TourOrchestrator、地图、景点详情 | 数字人贯穿路线推荐、到点讲解、下一站引导 |
| 其他创新探索 | 旅行记忆、手帐、行为分析 | 把导览过程沉淀成可展示成果 |

### 2.2 形象生成与驱动要求

截图提到“风格逼真、贴合氛围、灵活配置、口型同步、表情配合、动作可选、2D/3D 可选”。移动端应形成两层目标：

1. 演示层：让小灵像一个真实导游，而不是技术 Demo。
2. 工程层：让 VRM 在真机、弱网、低端设备上稳定可用。

当前项目已经具备 3D VRM、TTS、字幕、口型估算、表情动作时间线和全局浮窗能力，后续应重点补齐“自然度”和“稳定性”的验收闭环。

### 2.3 核心技术指标

| 指标 | 目标 | 验收方式 |
|---|---:|---|
| 语音问答端到端延迟 | <= 5s | 记录 ASR/RAG/TTS 各阶段耗时 |
| 文本问答首字返回 | <= 2.5s | SSE 或本地 FAQ 命中计时 |
| TTS 首句开始播放 | <= 2s | 移动端埋点记录首次播放时间 |
| 知识问答准确率 | >= 90% | 100+ 标准题库自动评测 |
| 口型自然度 | 明显匹配语音，无长时间空口型 | 录屏人工复核 + 自动时长一致性测试 |
| 系统稳定性 | 20 分钟演示无崩溃 | 真机连续导览测试 |
| 低端设备兜底 | 不白屏、不阻塞主流程 | 2D/静态 fallback + 降帧策略 |

## 3. 当前基础判断

现有移动端已经具备比较好的 VRM 基础，可以在此基础上强化，而不需要重做。

### 3.1 已有能力

- `useDigitalHumanDriver` 已统一承接 TTS、字幕、口型、表情、动作等数字人驱动逻辑。
- `VRMView` 已支持 `full` 和 `float` 两种渲染模式，并区分浮窗与完整模式的像素比。
- `VRMProvider` 已支持全局浮窗延迟挂载，并能在页面内 VRM 舞台存在时隐藏全局浮窗。
- `VRMManager` 已具备数字人状态、页面上下文、讲话事件、模型加载和缓存能力。
- `textTimeline` 已具备中文文本分句、表情识别、动作识别和时间线播放能力。
- 移动端已有导览状态、路线、地图、景点详情、聊天和旅行记忆等页面基础。

### 3.2 主要差距

1. 数字人主角感还不够强：部分页面仍像“景区 App + 数字人组件”，不是“数字人带你游”。
2. 口型、字幕、真实 TTS 时长之间仍需要更严格对齐，避免长文本播报时字幕或口型提前结束。
3. 表情动作需要从“关键词触发”升级为“场景语义触发”，保证比赛演示稳定。
4. 低端机、弱网、WebGL 异常、TTS 失败等场景需要更明确的降级路径。
5. 评审指标需要可复测报告，而不只是功能说明。

## 4. 优化目标

### 4.1 产品目标

让用户在移动端感受到“小灵是导游本人”：

- 打开 App 后，小灵主动出现并说明能做什么。
- 用户不用理解复杂功能入口，只需要回答“玩多久、想看什么”。
- 到达景点时，小灵主动讲解，并可被打断、追问、重播。
- 游览结束后，小灵帮助生成旅行记忆和游玩总结。

### 4.2 技术目标

让系统可以被评测、被演示、被兜底：

- 问答准确率、语音延迟、TTS 播放、VRM 渲染稳定性都有指标。
- 关键能力在离线演示模式下可运行。
- VRM 渲染失败时主流程不崩溃。
- 同一页面不出现多个 VRM 实例争抢性能。

## 5. 重点优化方案

### 5.1 首屏舞台化

将首页或探索页的首屏改成“小灵主动导览舞台”：

- 中心区域展示页面内 VRM，而不是只显示右下角浮窗。
- 背景使用灵山实景图或东方山水氛围图，突出景区场景。
- 小灵气泡展示一句主动引导，例如：“我可以按你的时间，带你走一条最合适的路线。”
- 主操作保留 3 个：开始导览、自由探索、问小灵。
- 页面内有 VRM 舞台时，隐藏全局右下角浮窗，避免重复出现。

预期效果：第一眼建立“这是数字人导览系统”的认知，而不是普通旅游信息页。

### 5.2 统一数字人驱动

继续以 `useDigitalHumanDriver` 作为唯一上层驱动入口，避免页面各自维护口型、动作和字幕逻辑。

建议接口保持如下方向：

```ts
type DigitalHumanDriver = {
  speak(text: string, options?: SpeakOptions): void;
  stop(options?: StopSpeakingOptions): void;
  setExpression(expression: Emotion): void;
  playAction(action: Action, durationMs?: number): void;
  setPageContext(context: PageContext, data?: Record<string, unknown>): void;
};
```

所有页面只调用 `driver.speak()`、`driver.stop()`、`driver.setPageContext()`，不要直接复制 `ExpressionPlayer`、`textToTimeline` 或 `useVRMSync` 逻辑。

使用页面级 `PageDigitalHumanDock` 时，空闲状态常驻“小灵 · 随时为你讲解”气泡；说话时由当前字幕替换，结束后自动恢复，避免隐藏全局浮窗后页面只剩模型而失去文字提示。

### 5.3 口型、字幕、语音对齐

移动端讲解的自然度主要取决于三件事是否同步：声音、字幕、嘴型。

优化建议：

1. 优先使用真实 TTS 音频时长驱动字幕和口型。
2. 没有真实音频时长时，统一使用 `estimateSpeechDuration` 估算。
3. 长文本按句子切分，字幕逐句滚动，不要一次性展示完整长文。
4. 播报被打断时，立即清空口型、字幕和动作状态。
5. TTS 失败时保留文字回答，并让小灵使用“抱歉/说明”表情，而不是静默失败。

验收标准：

- 讲解 30 秒长文本时，字幕不会提前全部出现。
- 语音结束后 500ms 内口型恢复自然闭合。
- 用户点击“停止讲解”后，声音、字幕、嘴型、动作同时停止。

### 5.4 表情与动作语义化

不要让动作太频繁，重点是“少而准”。建议建立稳定映射：

| 场景 | 表情 | 动作 | 说明 |
|---|---|---|---|
| 首次欢迎 | happy | wave | 建立亲和力 |
| 推荐路线 | happy | point | 引导用户看路线/地图 |
| 历史文化讲解 | thinking/relaxed | lookUp | 表达思考与讲述感 |
| 宏伟景点介绍 | surprised | lookUp | 配合“大佛高度、建筑规模”等内容 |
| 用户感谢 | grateful/happy | bow | 有礼貌的反馈 |
| 未知问题/资料不足 | sad | shakeHead | 明确不编造 |
| 到点导航提醒 | neutral/happy | point | 指向下一步操作 |
| 完成游览 | happy/grateful | clap 或 bow | 形成结束仪式感 |

控制原则：

- 每句话最多触发一个主动作。
- 动作持续时间跟随当前语音片段，不要跨句残留。
- 只有“请看、这边、前方、左侧、右侧”等明确方向表达触发 `point`；普通路线、景点和历史介绍保持讲解动作。
- 红衣导览 VRM 的原生 `Surprised` 会呈现眯眼微笑，因此移动端 `surprised` 使用眼睑展开与 `O` 圆嘴组合，不叠加 `happy`。
- 说话期间只保留呼吸、眨眼、当前讲解动作和实时口型，不调度随机 waiting 动作。
- 连续问答时降低动作频率，避免干扰阅读。
- 提供“减少动效”设置，适配低端机和无障碍需求。

### 5.4.1 表情动作丰富化 Demo

表情动作丰富化的目标不是让小灵一直动，而是让她在正确场景里有正确的小反应。建议先做一个独立 Demo，用于验证“小灵是否更像真人导游”，再合入正式导览流程。

#### Demo 目标

1. 展示小灵从“静态回答者”升级为“有状态的导游”。
2. 验证表情、动作、注视、头部朝向和字幕是否能被统一驱动。
3. 给比赛演示准备一组稳定可复现的表现片段。
4. 为后续真实业务场景沉淀 `PerformancePreset` 表现包。

#### 表情层：从标签升级为强度

当前 `happy`、`sad`、`thinking` 等离散表情可以继续保留，但 Demo 层建议增加强度和细节字段：

```ts
type ExpressionProfile = {
  emotion: Emotion;
  intensity: number;
  mouth?: 'neutral' | 'smile' | 'open' | 'soft';
  eyes?: 'normal' | 'soft' | 'wide' | 'thinking';
  brow?: 'neutral' | 'raised' | 'concerned';
  durationMs: number;
};
```

推荐先做 9 个表情 profile：

| Profile | 用途 | 说明 |
|---|---|---|
| `warmSmile` | 首次欢迎 | 轻微微笑，亲和但不过度兴奋 |
| `softNarrating` | 景点讲解 | 平稳讲述，适合长文本 |
| `thinking` | 思考答案 | 眼神略上移，头部轻微倾斜 |
| `amazed` | 宏伟景点介绍 | 眼睛略张，配合抬头 |
| `grateful` | 感谢用户 | 微笑 + 轻微低头 |
| `hesitant` | 不确定 | 眉头轻收，语气谨慎 |
| `apologetic` | 答不上来 | 轻微抱歉，不编造答案 |
| `confident` | 推荐路线 | 正向、稳定、有引导感 |
| `cheerful` | 完成打卡/总结 | 比 warmSmile 更明亮 |

#### 动作层：大动作和小动作分离

Demo 中动作分两类：

| 类型 | 动作 | 用途 |
|---|---|---|
| 大动作 | `wave` | 欢迎用户、首次出现 |
| 大动作 | `point` | 指向地图、路线、下一站 |
| 大动作 | `present` | 展示路线卡片或推荐结果 |
| 大动作 | `invite` | 邀请用户开始导览 |
| 大动作 | `bow` | 感谢、结束总结 |
| 大动作 | `clap` | 完成打卡、路线完成 |
| 小动作 | `blink` | 常驻自然眨眼 |
| 小动作 | `breathe` | 常驻呼吸起伏 |
| 小动作 | `nodSoft` | 讲解中轻点头 |
| 小动作 | `glanceLeft` / `glanceRight` | 等待或思考时扫视 |
| 小动作 | `tiltHeadSoft` | 倾听用户输入 |
| 小动作 | `listeningLean` | 用户说话时轻微前倾 |

大动作由业务场景触发，小动作由状态机持续驱动。这样可以避免“每句话都大幅摆动”的不自然感。

#### 注视层：让小灵知道自己在看哪里

注视和头部朝向比单纯换表情更能提升真实感。Demo 建议支持：

```ts
type GazeTarget = 'user' | 'map' | 'routeCard' | 'spotImage' | 'up' | 'left' | 'right' | 'down';
```

| 场景 | 注视目标 |
|---|---|
| 用户说话 | `user`，头部轻微前倾 |
| 推荐路线 | `routeCard`，随后回到 `user` |
| 地图导航 | `map`，配合 `point` |
| 介绍大佛高度 | `up`，配合 `amazed` |
| 思考答案 | `left` 或 `right`，短暂停留 |
| 答不上来 | `down`，随后回到 `user` |

#### 场景表现包

建议优先实现 8 个 `PerformancePreset`，覆盖比赛演示最常见场景：

| Preset | 触发场景 | 表情 | 动作 | 注视 | 字幕/语音示例 |
|---|---|---|---|---|---|
| `welcomeGuide` | 打开 App | `warmSmile` | `wave` | `user` | 欢迎来到灵山胜境，我是你的数字导游小灵。 |
| `listenUser` | 用户按住说话 | `softNarrating` | `listeningLean` | `user` | 我在听，请告诉我你想怎么玩。 |
| `thinkingAnswer` | 等待回答生成 | `thinking` | `tiltHeadSoft` | `left` | 我来帮你整理一下最合适的路线。 |
| `routePresent` | 推荐路线 | `confident` | `present` | `routeCard` | 这条路线适合一小时游览，重点看灵山大佛和九龙灌浴。 |
| `spotNarration` | 到点讲解 | `softNarrating` | `nodSoft` | `spotImage` | 这里是灵山大佛，是景区最具代表性的地标。 |
| `amazedIntro` | 宏伟景观 | `amazed` | `lookUp` | `up` | 灵山大佛高达八十八米，站在脚下会非常震撼。 |
| `apologizeUnknown` | 资料不足 | `apologetic` | `shakeHead` | `down` | 这个问题资料里暂时没有明确提到，我不能随便编造。 |
| `tourComplete` | 完成游览 | `cheerful` | `clap` 或 `bow` | `user` | 今天的路线完成啦，我可以帮你生成一份旅行记忆。 |

建议的类型草案：

```ts
type PerformancePreset = {
  id: string;
  expression: ExpressionProfile;
  primaryAction: Action;
  secondaryMotion?: 'calmIdle' | 'talkingIdle' | 'listeningIdle';
  gaze: GazeTarget;
  headRotation?: { x: number; y: number };
  durationMs: number;
  speechText: string;
};
```

#### Demo 页面建议

新增一个内部演示入口，例如：

```text
software/mobile/app/vrm-performance-demo.tsx
```

页面结构：

1. 顶部：页面标题“数字人表情动作 Demo”。
2. 中部：页面内 `VRMView` 舞台，展示小灵。
3. 下方：8 个表现包按钮，点击后播放对应 `PerformancePreset`。
4. 右下：状态面板，显示当前 `expression`、`action`、`gaze`、`durationMs`。
5. 底部：停止播放、减少动效、循环播放三个控制项。

Demo 页面不接入复杂后端，只验证本地表现能力。所有文案、动作和时长写在本地数组里，方便答辩前快速调参。

#### Demo 验收标准

- 点击 8 个表现包按钮，小灵都有不同且可辨认的表现。
- 欢迎、路线推荐、景点讲解、未知问题、完成总结五个场景必须稳定。
- 表情切换不突兀，动作结束后回到自然 idle。
- 注视方向变化明显，但不夸张。
- 停止播放后，字幕、口型、动作、注视全部复位。
- 开启“减少动效”后，大动作减少，小动作和字幕仍保留。

### 5.5 主动导览闭环

VRM 的价值应从聊天页扩展到完整导览流程。

建议状态机：

```text
IDLE
  -> GREETING
  -> PREFERENCE_COLLECTING
  -> ROUTE_SUGGESTED
  -> NAVIGATING
  -> ARRIVED
  -> NARRATING
  -> QA_FOLLOW_UP
  -> NEXT_RECOMMENDATION
  -> COMPLETED
  -> MEMORY_SUMMARY
```

关键交互：

- 首页：小灵主动问“你今天大概玩多久？”
- 路线页：小灵说明为什么推荐这条路线。
- 地图页：小灵提示下一站方向、距离和预计时间。
- 景点详情页：小灵到点讲解，并支持追问。
- 记忆页：小灵总结今天走过哪里、问过什么、适合下次去哪。

### 5.6 多模态交互完善

移动端必须同时支持语音和文字，不能只依赖语音。

建议保留以下入口：

- 按住说话或点击录音。
- 文字输入。
- 快捷问题。
- 停止播报。
- 重新播放。
- 静音模式。
- 演示模式快捷问题。

语音按钮需要明确状态：

| 状态 | 文案/反馈 |
|---|---|
| 待录音 | 按住问小灵 |
| 录音中 | 正在听你说 |
| 识别中 | 正在识别 |
| 回答中 | 小灵正在回答 |
| 失败 | 识别失败，可重新说或打字 |

### 5.7 性能与稳定性降级

移动端 VRM 的风险主要来自 WebGL、模型加载、长时间渲染和页面切换。

建议策略：

1. 浮窗模式限制像素比和帧率，完整舞台模式再提高质量。
2. 页面切换后延迟挂载 VRM，避免和导航动画抢资源。
3. 同一页面只保留一个 VRM 实例。
4. WebGL 创建失败或模型加载失败时，切换到静态/2D 形象。
5. 低端设备默认关闭阴影、降低抗锯齿和动作频率。
6. 长时间后台或页面不可见时暂停渲染循环。
7. 比赛演示前用真机连续运行 20 分钟。

降级路径：

```text
3D VRM full
  -> 3D VRM float low quality
  -> 2D animated avatar
  -> static avatar + subtitle + audio
  -> text-only guide
```

最低保障是“主流程不断”：即使 3D 形象失败，导览、问答、字幕、路线仍然可用。

### 5.8 演示模式保障

比赛现场网络、TTS、后端模型都可能不稳定，必须准备演示模式。

建议内置：

- 2-3 条标准路线。
- 20-30 条高频 FAQ。
- 3-5 段核心景点讲解词。
- 对应字幕和预生成音频。
- 一键切换演示模式的环境变量或设置入口。
- 后端不可用时自动显示“演示数据模式”，但不影响主流程。

演示主线建议：

1. 打开 App，小灵欢迎并推荐路线。
2. 用户说“我只有一小时，想看最经典的景点”。
3. 小灵生成路线并进入地图导览。
4. 到达灵山大佛，小灵自动讲解。
5. 用户追问一个历史文化问题。
6. 系统展示来源可靠的回答。
7. 游览结束，生成旅行记忆。
8. 后台展示移动端行为数据。

## 6. 实施优先级

### P0：比赛演示基线

目标：保证现有数字人链路稳定、可演示。

- 固化 3-5 个数字人演示场景：欢迎、路线推荐、到点讲解、感谢、未知问题。
- 先做 `vrm-performance-demo`，沉淀 8 个表情动作表现包。
- 校准字幕、口型、语音时长一致性。
- 加强停止播报逻辑，避免长讲解阻塞后续点击。
- 明确页面内 VRM 与全局浮窗的互斥策略。
- 输出一份演示脚本和验收清单。

### P1：主角感与主动导览

目标：让小灵成为移动端首屏主角。

- 首页或探索页首屏改为数字人导览舞台。
- 入口文案改成“小灵带你游”的导览语气。
- 路线、地图、景点详情、聊天页共享同一导览状态。
- 到点讲解和下一站推荐由小灵主动发起。

### P2：问答准确率和语音延迟

目标：补齐核心技术指标。

- 扩充 100+ 标准问答题库。
- 本地 FAQ 优先命中高频问题。
- 后端 RAG 回答必须带来源。
- 统计文本问答首字时间、语音问答总时间、TTS 首播时间。
- 输出准确率报告和延迟报告。

### P3：性能降级与真机验收

目标：确保现场不翻车。

- 增加 2D/静态形象 fallback。
- 低端模式降低像素比、阴影、动作频率。
- 真机连续 20 分钟导览测试。
- 覆盖定位拒绝、麦克风拒绝、弱网、后端不可用场景。

### P4：答辩亮点增强

目标：形成作品记忆点。

- 强化旅行记忆/手帐。
- 后台展示路线完成率、景点热度、问答热词、用户偏好。
- 支持数字人形象、服装、音色配置。
- 形成“游客端 + 管理端 + 数据回流”的完整闭环。

## 7. 验收清单

### 7.1 体验验收

- [ ] 首屏能明确看到小灵数字人。
- [ ] 小灵能主动欢迎并推荐下一步。
- [ ] 用户可通过文字和语音提问。
- [ ] 所有语音回答都有同步字幕。
- [ ] 长文本讲解可停止、可重播。
- [ ] 到点讲解后能继续追问。
- [ ] 游览结束能生成旅行记忆。

### 7.2 自然度验收

- [ ] 欢迎场景触发微笑和挥手。
- [ ] 路线推荐触发指向动作。
- [ ] 历史讲解触发思考表情。
- [ ] 宏伟景点介绍触发惊叹表情。
- [ ] 未知问题触发抱歉/摇头反馈。
- [ ] `welcomeGuide`、`listenUser`、`thinkingAnswer`、`routePresent`、`spotNarration`、`amazedIntro`、`apologizeUnknown`、`tourComplete` 八个表现包可稳定播放。
- [ ] 注视目标能在用户、地图、路线卡片、景点图、上方和下方之间切换。
- [ ] 动作结束后能回到自然 idle。
- [ ] 连续问答时动作不过频。

### 7.3 技术指标验收

- [ ] 文本问答首字返回 <= 2.5s。
- [ ] 语音问答端到端 <= 5s。
- [ ] TTS 首句开始播放 <= 2s。
- [ ] 标准题库准确率 >= 90%。
- [ ] 连续 20 分钟演示无崩溃。
- [ ] 后端不可用时可进入演示模式。
- [ ] WebGL 异常时可降级，不影响导览主流程。

## 8. 答辩表达建议

一句话定位：

> 我们做的不是一个会说话的 3D 形象，而是一个能规划、能带路、能讲解、能问答、能记录游客行为的移动端 AI 数字人导游。

技术表达：

> 移动端采用 VRM 3D 数字人作为交互入口，通过统一的 DigitalHumanDriver 驱动 TTS、字幕、口型、表情和动作。导览流程由 TourOrchestrator 管理，结合地图、景点、路线和知识问答形成完整闭环。系统同时提供本地 FAQ、演示模式和低性能降级，保证比赛现场稳定演示。

亮点表达：

1. 小灵不是装饰，而是贯穿路线规划、地图导航、景点讲解、问答和旅行记忆的主导角色。
2. 数字人的口型、字幕、表情和动作由统一时间线驱动，提升自然度。
3. 高频问题本地优先，复杂问题走 RAG，回答带来源，目标准确率不低于 90%。
4. 支持弱网和低端设备降级，确保现场演示稳定。
5. 游客行为会回流后台，服务景区运营分析。
